# 系统架构

## 设计目标

核心目标不是追求极低延迟，而是让个人投资者能够审计每一笔套利交易，并在柜台、行情或双腿成交出现异常时默认停止扩大风险。

## 数据流

```text
CTP / CSV
   ↓
Broker
   ↓ Tick / Order / Trade / Account / Position
TradingEngine
   ├── CalendarSpreadStrategy
   ├── RiskManager
   ├── PairExecutor
   ├── StateStore
   └── AuditJournal
          ↓
       Broker
          ↓
     Sim / CTP
```

策略层不知道 CTP SDK，CTP 也不知道策略规则。所有模块只交换 `models.py` 中的内部对象，所以回放、模拟和实盘复用同一条业务链路。

## 双腿执行

跨期套利不是原子交易。系统把两腿分别提交为带组合 `reference` 的 FAK 限价单，并使用一档盘口加可配置的主动价差提高成交概率。

如果第二腿提交失败：

1. 撤销已经提交但仍活动的第一腿。
2. 如果第一腿已经成交，只允许对第一腿反向减仓。
3. 引擎持续检查组合是否等量反向。
4. 超过 `legging_timeout_seconds` 仍失衡时，尝试减仓修复并进入持久化停机。

系统不会为了“补齐套利组合”在异常路径继续开另一条风险腿。

## 持仓和交易日

持仓分为多头今仓、多头昨仓、空头今仓、空头昨仓。上期所和能源中心平仓时显式拆分 `CLOSE_TODAY`/`CLOSE_YESTERDAY`；其他交易所使用普通 `CLOSE`。

CTP 实盘优先读取柜台交易日，避免夜盘直接按自然日切换日亏损基线。模拟回放则使用 CSV 的 `trading_day`。

## 状态恢复

状态文件保存：

- 持久化停机开关和原因；
- 交易日与日初权益；
- 权益高水位；
- 本地持仓快照；
- 策略滚动价差历史、方向和入场统计量。

实盘重启时不会用新读取的柜台持仓覆盖旧状态后再“对账”。系统先保留本地快照，与柜台真实持仓比较；不一致即停机。

## 风险边界

静态合约配置用于**事前保守估算**，实际账户权益和可用资金以柜台快照为准。保证金估算按双腿相加，并乘以安全缓冲，不假设交易所一定给予套利组合保证金优惠。

系统适合低频个人套利，不适合盘口做市、微秒级高频或依赖席位延迟优势的策略。
